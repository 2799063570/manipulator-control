# 机器人开发多线程与实时性学习手册

> 目标：能为机器人软件正确划分“控制、通信、感知、规划、UI/日志”工作，安全交换数据，理解 ROS 2 的回调调度，并清楚地说明普通多线程与实时控制的边界。

## 1. 先建立正确认识

机器人开发中学多线程，不是为了“线程越多越快”，而是为了同时处理不同节奏、不同阻塞风险的工作：例如 1 kHz 的控制周期、100 Hz 的状态反馈、30 Hz 相机、耗时不确定的路径规划，以及可能阻塞的网络/串口通信。

最重要的一条边界：**ROS 2 回调、MoveIt 规划和普通 Linux 线程默认都不是硬实时控制循环。** 电流环、速度内环等硬实时任务通常留在驱动器或 MCU；上位机 ROS 2 负责规划、较慢的目标命令、状态估计和监控。

```mermaid
flowchart LR
  S[传感器 / 控制柜 / MCU] -->|阻塞 I/O| N[通信线程]
  N -->|最新状态 + 时间戳| C[控制循环]
  P[ROS 2 回调线程] -->|目标命令| C
  C -->|预分配命令缓冲| N
  M[MoveIt / 规划线程] -->|低频轨迹目标| P
  C -->|降频状态 / 诊断| V[日志、RViz、记录]
```

这里的核心不是线程数，而是数据从哪里来、谁拥有它、谁能等待、超过多久必须安全停止。

## 2. 学习优先级

| 优先级 | 必须掌握 | 在机器人中的用途 |
|---|---|---|
| P0 | `std::thread` / `std::jthread` 生命周期、`join`、异常与退出信号 | 正确启动和停止通信线程、spinner 线程 |
| P0 | 竞态条件、`std::mutex`、`lock_guard`、`unique_lock` | 保护共享的状态、命令、故障标志 |
| P0 | `std::condition_variable`、生产者-消费者 | 低频任务队列、等待新任务；不用于高频控制的每周期等待 |
| P0 | `std::atomic`、数据竞争、内存可见性 | 停止标志、计数器、最新序号/时间戳 |
| P1 | ROS 2 executor、callback group、单/多线程 executor | 防止回调互相阻塞或意外并发访问共享状态 |
| P1 | 超时、状态机、背压、队列长度 | 通信中断、旧命令、规划积压时的安全处理 |
| P1 | 实时性基本原则：预分配、短临界区、无阻塞 I/O | 写 `ros2_control` 硬件接口或准实时节点时避免抖动 |
| P2 | SPSC 无锁环形缓冲、内存序、线程优先级、实时内核 | 有明确性能测量和需求后再学；不作为入门第一步 |

不要一开始学习线程池、协程、复杂 lock-free 容器或手写无锁算法。面试中能把 `mutex + 短临界区 + 超时状态机` 用对，通常比炫耀无锁代码更有价值。

## 3. 第一部分：C++ 并发基础要学到什么程度

### 3.1 线程生命周期

要能回答并实践：线程为什么必须 `join()` 或 `detach()`？为什么机器人程序几乎不应随手 `detach()`？答案是：分离线程难以确定何时结束，可能在所属对象和 ROS 上下文已销毁后继续访问内存。

优先使用 C++20 的 `std::jthread`：它离开作用域会自动 join，并可接收 `std::stop_token` 作为协作式停止信号。若项目必须使用 `std::thread`，则以 RAII 方式保证异常路径也 `join()`。

```cpp
std::atomic<bool> running{true};
std::thread worker([&] {
  while (running.load(std::memory_order_relaxed)) {
    // 收取一次通信或执行一次低频工作；等待必须有超时。
  }
});

// 退出顺序：先停止接收新工作，再通知线程退出，最后 join。
running.store(false, std::memory_order_relaxed);
worker.join();
```

验收：你能写一个每 10 ms 增加计数的工作线程，主线程在 1 秒后请求停止并稳定退出 100 次，没有崩溃或卡死。

### 3.2 数据竞争与互斥锁

当两个线程同时读写同一个非原子对象，且至少有一个是写操作，就可能产生数据竞争；它不是“偶尔读到旧值”这么简单，而是未定义行为。

机器人常见共享对象包括：关节状态数组、目标关节值、最新传感器帧、连接状态、错误码、轨迹队列。

最先掌握的安全模式是：**锁保护共享对象；锁内仅复制；锁外计算、日志和网络 I/O。**

```cpp
struct RobotState {
  std::array<double, 6> position{};
  std::array<double, 6> velocity{};
  std::chrono::steady_clock::time_point stamp{};
};

std::mutex state_mutex;
RobotState latest_state;

// 通信线程：很短地写入最新状态。
void updateState(const RobotState & received) {
  std::lock_guard<std::mutex> lock(state_mutex);
  latest_state = received;
}

// 控制线程：很短地复制，再在锁外处理。
RobotState snapshotState() {
  std::lock_guard<std::mutex> lock(state_mutex);
  return latest_state;
}
```

`lock_guard` 适用于“进入作用域即上锁、离开即解锁”；`unique_lock` 适用于需要延迟加锁、手动解锁或与条件变量配合的场景。除非确实需要，不要手写 `mutex.lock()` / `unlock()`。

验收：用 ThreadSanitizer（`-fsanitize=thread`，若环境支持）或反复压测，先复现一个未加锁的计数器错误，再用 `mutex` 或 `atomic` 修复它。

### 3.3 条件变量与队列

条件变量适合“没有任务就睡眠，有任务才唤醒”的低频工作线程，如地图保存、日志写盘、耗时规划任务。等待必须使用谓词，以应对虚假唤醒。

```cpp
std::mutex queue_mutex;
std::condition_variable queue_cv;
std::queue<Task> tasks;
bool stopping = false;

// 消费者：谓词同时处理有任务与停止两种情况。
void worker() {
  for (;;) {
    std::unique_lock<std::mutex> lock(queue_mutex);
    queue_cv.wait(lock, [] { return stopping || !tasks.empty(); });
    if (stopping && tasks.empty()) return;
    Task task = std::move(tasks.front());
    tasks.pop();
    lock.unlock();
    execute(task);
  }
}
```

对控制命令不能无限排队：例如 joystick 或 `cmd_vel` 应通常只保留**最新命令**并附时间戳，超过命令超时就输出零速度；不能让 2 秒前的命令在网络恢复后才执行。

### 3.4 atomic：先学正确用法

适合原子变量的对象：`running` 停止标志、简单状态码、计数器、最新序列号。它不自动让一组关节数组“整体一致”，也不能替代对复合对象的锁。

- 先会使用默认内存序；对停止标志可显式使用 `memory_order_relaxed`。
- 不要把所有共享数据改成 atomic；这会增加复杂度，并不能保证多字段快照的一致性。
- 只有已经证明锁竞争影响周期、且数据模型是单生产者单消费者时，再考虑 SPSC 环形缓冲。

## 4. 第二部分：ROS 2 的并发模型

### 4.1 node 不是线程，callback 由 executor 调度

ROS 2 中订阅回调、timer、service/action 回调都要由 executor 执行。`rclcpp::spin(node)` 常用的是单线程 executor；一个耗时 callback 会延迟同 executor 上的其他 callback。

| 选择 | 适合什么 | 风险与约束 |
|---|---|---|
| `SingleThreadedExecutor` | 初学、共享状态较多、回调短小 | 一个慢回调可饿死其他回调；但同 executor 内更容易推理顺序 |
| `MultiThreadedExecutor` | 有独立的耗时回调，且已设计好同步 | 回调可并发，必须保护共享状态、明确 callback group |
| 独立 `std::thread` | SDK 阻塞 I/O、第三方库阻塞调用 | 需明确停止、join、数据交换和超时 |

### 4.2 callback group 的实际作用

- `MutuallyExclusive`：同一组内一次只运行一个回调。适合共享状态多、需要串行访问的回调。
- `Reentrant`：同一组内回调可并发甚至重入。仅在回调无共享可变状态或已完全同步时使用。

常用设计不是“所有东西 Reentrant”，而是：控制相关 timer 与命令回调放在一个互斥组；耗时的文件/规划/服务回调放到另一个组或独立线程。这样通信和安全回调不会被一次长规划完全阻塞。

### 4.3 本仓库的现有样例

[`moveit_cpp_demo.cpp`](../robot_control_ros2/src/simple_arm_moveit_config/src/moveit_cpp_demo.cpp) 和 [`planner_comparison.cpp`](../robot_control_ros2/src/simple_arm_moveit_config/src/planner_comparison.cpp) 都创建了 `SingleThreadedExecutor`，再用一个 `std::thread` 调用 `executor.spin()`。主线程可同步调用 `MoveGroupInterface` 规划，spinner 线程则持续处理 ROS 通信。

这是一种合理的**客户端并发模式**，需要学会其退出顺序：`executor.cancel()` → `spinner.join()` → `rclcpp::shutdown()`。它不意味着规划线程是实时线程，也不应在 spinner 中执行长时间阻塞工作。

## 5. 第三部分：实时性与机器人控制的规则

### 5.1 控制循环中禁止或应极力避免的事

| 行为 | 为什么有风险 | 替代方案 |
|---|---|---|
| 网络、串口、磁盘阻塞等待 | 耗时不可预测，直接错过周期 | 交给通信/记录线程；控制循环读最新快照 |
| 每周期 `new`、`vector` 扩容、字符串拼接 | 分配器延迟不可预测 | 启动时预分配 `std::array`/缓冲区 |
| 等待 mutex 很久 | 优先级反转和周期抖动 | 临界区只复制；必要时使用 SPSC 缓冲 |
| 高频 `RCLCPP_INFO` / `std::cout` | I/O 慢且可能加锁 | 降频诊断、环形日志或计数器 |
| 无界任务队列 | 旧命令堆积，恢复后发生危险动作 | 最新值覆盖、队列上限、过期即丢弃 |

### 5.2 最小安全架构

以机械臂真机接口为例：

1. 通信线程从控制柜读取整包状态，写入“最新状态 + 单调时间戳”。
2. `read()` 只快速复制该快照，并检查是否过期。
3. 控制器基于新鲜状态计算命令；`write()` 只快速更新“最新命令”。
4. 通信线程取最新命令并发送；通信失败、急停或状态过期均进入故障状态并安全停止。
5. 规划、可视化和日志永远不能阻塞以上链路。

本仓库的 [AUBO 参考驱动手册](30-AUBO参考驱动-仿真到真机实施手册.md) 已明确将阻塞通信与控制循环隔离，并在 `read()` 中检查反馈新鲜度；[移动机器人真机部署](06-移动机器人真机部署.md) 说明了 MCU/驱动器与 ROS 上位机的实时职责分层。

### 5.3 必须测量的指标

不要只说“多线程更快”。至少记录：

- 控制周期的平均值、最大值、P95/P99 抖动。
- 状态反馈年龄：`now - state.stamp`；超过阈值的次数。
- 命令年龄与丢弃次数。
- 每个队列的最大长度和溢出次数。
- 锁持有时间与等待时间（先用简单打点统计）。
- 故障发生到安全停止的最大时间。

## 6. 四周学习与练习路线

每周 4 次 × 60–90 分钟即可；每个练习先写单线程版本，再故意制造问题，最后修复。所有练习都应保留代码、命令和结果。

### 第 1 周：线程、锁、停止

- 写“通信线程每 10 ms 更新状态，主线程每 20 ms 读取快照”的 C++ 小程序。
- 先去掉锁，观察计数或状态不一致；再以 `mutex + lock_guard` 修复。
- 加入 `atomic<bool>` 停止标志，保证无论正常或异常退出都 join。
- 口述题：`detach` 为什么危险？`atomic` 为什么不能替代整个 `RobotState` 的锁？

### 第 2 周：队列、超时与状态机

- 写生产者消费者队列：生产者模拟 10 Hz 指令，消费者模拟耗时任务。
- 为队列增加上限；超过上限丢弃旧任务或拒绝新任务，并记录计数。
- 另写“最新命令槽”：只保留最新值和时间戳，超过 100 ms 输出安全零命令。
- 口述题：为什么轨迹任务可排队，而连续速度命令通常不能排队？

### 第 3 周：ROS 2 executor 与 callback group

- 写一个 ROS 2 C++ 节点：订阅命令、100 Hz timer、低频诊断 timer。
- 在单线程 executor 中故意让一个 callback 睡眠 200 ms，观察其他 timer 被延迟。
- 改为 `MultiThreadedExecutor`；只在已对共享数据加锁/分组后比较现象。
- 使用 `ros2 topic hz`、时间戳和日志记录实际周期；不要只凭“看起来动了”判断。

### 第 4 周：连接现有 MoveIt 与硬件接口概念

- 阅读本仓库两个 spinner 例子，画出主线程、executor 线程、MoveIt 服务/动作通信的关系。
- 阅读 AUBO 手册中的状态缓存与超时部分，画出通信线程与 `read()`/`write()` 的数据流。
- 完成一次故障演练设计：通信 100 ms 无反馈时，哪个线程检测、状态如何转换、命令如何归零、如何恢复。
- 口述题：为什么 MoveIt 规划不应放进 1 kHz 控制循环？

## 7. 面试必须能答的 10 个问题

1. 什么是数据竞争？为什么“读取通常没关系”是错误的？
2. `mutex`、`lock_guard`、`unique_lock`、`atomic` 分别解决什么问题？
3. 条件变量为什么要与谓词一起使用？
4. 线程退出时为何要 join？为什么不建议 detach？
5. ROS 2 的 node、callback、executor、OS 线程有什么关系？
6. `SingleThreadedExecutor` 和 `MultiThreadedExecutor` 如何选择？
7. callback group 的 `MutuallyExclusive` 与 `Reentrant` 有何区别？
8. 控制循环为什么避免动态内存、锁等待、打印日志与阻塞 I/O？
9. 通信线程与控制循环之间怎样交换“最新状态”和“最新命令”？
10. 状态反馈超时、命令超时、队列满分别该怎样安全处理？

推荐回答结构：先说原则（例如“控制循环不等待网络”），再说实现（“通信线程写带时间戳的预分配快照，`read()` 快速复制并检查超时”），最后说验证（“统计状态年龄和故障到零命令的时间”）。

## 8. 完成门槛

- [ ] 能用 `std::thread`/`std::jthread` 安全启动、停止、join 一个工作线程。
- [ ] 能解释并修复一个竞态条件；锁内只做复制。
- [ ] 能实现有上限的任务队列和“最新命令 + 超时”槽。
- [ ] 能解释 ROS 2 executor 与 callback group，并谨慎使用 `MultiThreadedExecutor`。
- [ ] 能区分普通并发、准实时和硬实时；不把 ROS 2 executor 当作硬实时循环。
- [ ] 能针对当前机械臂项目画出规划、ROS 回调、通信、控制与反馈的线程/数据流图。

> 结论：先把线程生命周期、数据竞争、短锁、时间戳、超时和 ROS 2 executor 学扎实。它们是机器人多线程的 80% 价值；无锁队列和实时调度只在你能测到锁竞争或周期抖动、并有明确性能目标时再进入。
