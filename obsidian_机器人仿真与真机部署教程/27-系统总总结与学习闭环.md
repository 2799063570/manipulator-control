# 系统总总结与学习闭环

## 1. 一张图理解整个工程

```mermaid
flowchart TD
  X[Xacro + YAML 路径/参数] --> U[完整 URDF]
  U --> R[RSP]
  R --> RD[/robot_description]
  R --> TF[/tf_static 与 /tf]
  JS[/joint_states] --> R
  RD --> H{硬件后端}
  H --> F[Fake: GenericSystem + ros2_control_node]
  H --> G[Gazebo: gz_ros2_control plugin]
  H --> E[真机: SystemInterface + ros2_control_node]
  F --> CM[controller_manager]
  G --> CM
  E --> CM
  CM --> J[JSB + JointTrajectoryController]
  J --> JS
  M[MoveIt move_group] --> P[前处理 -> OMPL -> 后处理]
  P --> A[FollowJointTrajectory Action]
  A --> J
  Q[QoS] -.决定消息能否匹配.-> RD
  Q -.决定状态/传感器时效性.-> JS
```

## 2. 每个组件只记一句职责

| 组件 | 一句话职责 |
|---|---|
| Xacro | 启动前将带参数的模型模板展开成 URDF |
| RSP | 将 URDF + joint states 转成 robot description 和 TF |
| ros2_control_node | Fake/真机的硬件与 controller manager 宿主 |
| gz_ros2_control | Gazebo 内部的硬件接口与 manager 宿主 |
| JointStateBroadcaster | 将 state interface 转成 joint states |
| JointTrajectoryController | 将带时间的关节轨迹转成 command interface |
| MoveIt move_group | IK、碰撞、规划、时间参数化、Action 执行 |
| Gazebo | 物理、接触、传感器与仿真时钟 |
| SystemInterface | 真机通信、反馈、命令、安全检查 |
| QoS | 定义 ROS 消息可靠性、历史和迟到订阅行为 |

## 3. 三种后端的最短记忆

```text
Fake：外部 ros2_control_node + GenericSystem；内存模拟。
Gazebo：内部 gz_ros2_control plugin + GazeboSimSystem；物理仿真。
真机：外部 ros2_control_node + 厂商 SystemInterface；真实控制柜。
```

## 5. 每次启动的检查顺序

```bash
ros2 node list
ros2 topic info /robot_description -v
ros2 topic echo /joint_states --once
ros2 run tf2_tools view_frames
ros2 control list_hardware_interfaces
ros2 control list_controllers
ros2 action list -t
```

先检查模型和状态，再检查 TF，再检查 hardware/controller，最后检查 MoveIt action。问题永远从底层状态向上排，不要一开始只在 RViz 点 Execute。
